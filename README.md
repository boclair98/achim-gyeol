# 아침결

> 어제의 뉴스에서 오늘의 흐름만 골라, 평일 아침 한 번에 읽는 브리핑

[오늘의 아침결](https://morningnews.coders.kr) · [서비스 원칙](https://morningnews.coders.kr/trust) · [지난 뉴스](https://morningnews.coders.kr/archive)

아침결은 뉴스의 양보다 **이해의 속도**를 중요하게 생각합니다. 중요한 소식을 짧고 분명하게 먼저 보여주고, 배경·핵심 사실·왜 중요한지·다음 확인 포인트와 원문 출처까지 한 흐름으로 이어 줍니다.

## 한눈에 보는 경험

1. **열기** — 평일 오전 7시 30분(한국 시간), 이 기기에 오늘의 브리핑이 도착합니다. 토요일·일요일에는 자동 수집과 정기 발송을 쉬며, 월요일에는 일요일 뉴스를 제공합니다.
2. **이해하기** — 한 줄 결론과 쉬운 설명으로 낯선 이슈의 맥락을 먼저 잡습니다.
3. **확인하기** — 핵심 사실과 함께 제공되는 원문 출처를 필요할 때 더 읽습니다.

회원가입 없이 알림을 등록할 수 있고, 등록한 기기에서 읽기 크기·관심 분야·읽을 분량을 조정할 수 있습니다.

## 제품 원칙

- **핵심부터**: 첫 화면에서 제목, 한 줄 결론, 이해 포인트를 먼저 제시합니다.
- **맥락까지**: 처음 접하는 사람도 따라올 수 있도록 배경과 영향 범위를 풀어 씁니다.
- **출처와 함께**: 요약을 사실처럼 소비하지 않도록 관련 원문과 확인 상태를 함께 표시합니다.
- **선택은 가볍게**: 관심 분야는 카드 순서를 조정할 뿐, 중요한 뉴스 자체를 숨기지 않습니다.
- **어디서나 읽기 쉽게**: 모바일에서는 한 손으로, 데스크톱에서는 넉넉한 폭과 일정한 이미지 비율로 읽습니다.
- **모르면 모른다고**: 더 확인이 필요한 내용과 정정 이력을 숨기지 않습니다.

## 제공 기능

### 오늘의 브리핑

정책·경제·금융·사회·국제·테크·생활·문화·스포츠·e스포츠 등 여러 분야에서 전날의 중요한 흐름을 골라 제공합니다. 새 뉴스 홈은 대표 기사와 여러 곳에서 다룬 이슈부터 보여주고, 전체 기사를 분야·키워드·출처 수로 찾아볼 수 있습니다. 한 번에 12건을 표시하고 더 보기로 나머지를 이어 보여줍니다. 이는 화면 표시 단위이며 발행 상한이 아닙니다.

기사 한 편을 열면 다음 정보를 만날 수 있습니다.

- 제목과 한 줄 결론
- 낯선 이슈를 풀어 주는 이해 포인트
- 확인된 핵심 사실과 출처
- 왜 중요한지
- 앞으로 확인할 변수
- 여러 출처를 모아 읽기 쉽게 정리한 기사형 상세 내용

### 내 기기 맞춤 설정

알림은 기기 단위로 등록하며 이름·이메일·전화번호를 요구하지 않습니다. 글자 크기, 관심 분야, 요약 분량을 바꾸면 다음 방문과 다음 브리핑에도 이어집니다.

설정 화면에서 다음에 생기면 좋을 기능을 익명으로 선택할 수 있습니다. 현재 뉴스와 알림은 계속 무료이며, 선택 결과는 더 유용한 기능의 우선순위를 정하는 데만 사용합니다.

### 지난 브리핑 보관함

날짜·분야·검색어로 지난 브리핑을 다시 찾고, 다시 보고 싶은 에디션은 이 기기에 저장할 수 있습니다.

### 정정과 신뢰

뉴스마다 확인 상태를 표시하고, 오류 제보를 받으면 필요한 경우 정정 시각과 이유를 남깁니다. 중요한 판단을 앞두고는 카드 안의 원문과 공식 자료를 함께 확인하는 것을 권합니다.

## UI/UX 설계 방향

새 알림 하나를 누르면 [같은 발행일의 뉴스레터](https://morningnews.coders.kr/briefing/delivery/?date=2026-11-06)가 열립니다. 휴대폰과 PC 모두 제목 목록을 먼저 보여주고, 제목을 누르면 그 기사 한 편의 핵심 요약을 먼저 읽을 수 있습니다. 목록 복귀 시 눌렀던 제목으로 돌아옵니다. 발행된 모든 기사가 목록에 남고 사진 유무로 기사를 숨기지 않습니다.

직접 방문하는 [홈](https://morningnews.coders.kr/)과 [뉴스 페이지](https://morningnews.coders.kr/briefing/)는 별개입니다. 기존 뉴스 페이지의 대표 기사·검색·분야·출처순, 이전 공유 주소와 이미 받은 알림 링크는 그대로 사용할 수 있습니다.

- **읽기**: 한 줄 결론 → 자르지 않은 원본 사진 → 쉬운 설명 → 배경·중요성·근거·원문. 사진이 없거나 불러오지 못해도 텍스트는 남습니다.
- **정렬**: 편집 순서와 출처 많은 순을 제공합니다. 출처 수는 해당 기사에 연결된 서로 다른 출처를 뜻하며, 조회수나 실시간 검색량이 아닙니다.
- **실패 복구**: 기존 실제 발행본이 저장돼 있으면 날짜와 함께 표시합니다. 없으면 재시도와 지난 뉴스 안내를 보여주며 예시 뉴스로 채우지 않습니다.
- **접근성**: 기사 제목을 자르지 않고 충분한 터치 크기와 보이는 포커스를 둡니다. 키보드로 기사 선택·목록 복귀를 할 수 있고 상세에서 글자 크기를 바꿀 수 있습니다.

## 개발 시작하기

프런트 화면만 확인하려면 다음처럼 실행합니다.

```bash
cd frontend
pnpm install
pnpm dev
```

백엔드가 필요한 경우 별도 터미널에서 프로젝트의 표준 Spring Boot 실행 명령을 사용합니다. 자세한 값은 `backend/.env.example`을 참고하고, 비밀키·토큰·운영 자격 증명은 저장소에 커밋하지 않습니다.

### 저장소 구조

```text
frontend/   뉴스 화면, 알림 등록, 보관함, 서비스 원칙
backend/    브리핑·출처·알림·정정 API와 운영 로직
docs/       백업·복구 및 장애 대응 문서
```

## 메일 디자인 프로토타입

### 읽기 화면과 메일 시안의 구분

[메일 디자인 미리보기](https://morningnews.coders.kr/briefing/delivery/preview/?date=2026-11-06)는 실제 발행본으로 메일 HTML을 보여주며, 동일한 HTML과 텍스트 본문을 담은 `.eml` 파일을 받을 수 있습니다. 본문의 제목 링크는 그 발행일의 기사로 연결됩니다. 실제 운영 채널은 **웹 푸시**이며 이메일 발송 제공자는 연결되어 있지 않습니다. 미리보기를 열거나 다운로드해도 이메일·알림을 보내거나 구독을 갱신하지 않습니다.

`/briefing/`과 `/briefing/delivery/` 모두 실제 `/api/briefings/today` 또는 `/api/briefings/YYYY-MM-DD`만 읽습니다. 메일에 과도하게 큰 HTML을 넣어 내용이 잘리는 경우를 피하도록 크기 예외에는 전체 기사 링크를 제공합니다. 운영 웹 뉴스레터의 기사 수에는 제한을 추가하지 않습니다.

### 이전 정적 메일 디자인 실험

`frontend/public/newsletter-prototypes/`에는 아침편지·모닝브리프·데일리픽 시안과 정적 비교 화면이 있습니다. 2026년 9월 16일 보관 기사 6건을 사용하며 최신 뉴스나 실제 수신함이 아닙니다. 현재 운영 채널은 웹 푸시이고 이메일 발송 서비스는 연결 전입니다.

```bash
cd frontend
node scripts/export-newsletter-prototypes.mjs
node --test tests/newsletter-renderer.test.mjs
pnpm build
```

로컬 서버에서 `/newsletter-prototypes/`를 열어 비교할 수 있습니다. HTML·텍스트 렌더러는 발송 기능이나 키를 포함하지 않습니다. 실제 서비스 연결과 미확인 항목은 [메일 서비스 계획](docs/newsletter-service-plan.md)을 참고하세요. 이 프로토타입 제작은 배포·발송 승인이 아닙니다.

제목은 전체 폭으로 읽히며 사진은 원본 비율을 유지합니다. 비교 화면은 메일 본문 길이에 맞춰 늘어나 끝까지 읽을 수 있습니다. 네이버 뉴스·뉴닉·어피티·토스피드의 읽기 화면을 관찰한 [서체·가독성 조사](docs/newsletter-reference-audit.md)를 바탕으로 공식 SUIT(OFL-1.1)를 로컬에 포함했습니다. 폰트·라이선스·고정 커밋·해시는 `fonts/`에 있으며, 토스 전용 폰트와는 다릅니다. 아이폰 WebKit 캡처에서 가변 파일의 굵기가 지나치게 얇게 보이는 차이를 발견해 Regular·SemiBold·Bold 세 정적 파일을 사용합니다. 기본 아침편지의 쉬운 설명은18px/1.75, 배경은16px/1.75이며 모바일 안쪽 여백은20px입니다. 다른 메일 대안은 기존16–17px 기준을 유지하고 웹폰트 차단 시 기기 서체로 읽힙니다. 실제 사용자 선호 조사와 실제 메일앱 검증은 아직 진행하지 않았습니다.

후속 시안은 상단 제목·설명·분류·버튼까지 `theme.css`의 같은 서체를 사용하고, 밝은 바탕과 블루 포인트로 전체 위계를 통일했습니다. `/newsletter-prototypes/compare.html`에서는 이미지 합성 대신 세 메일 HTML을 마지막 이야기까지 직접 비교합니다. 갤러리와 비교 화면 사이를 이동할 수 있으며, 이 블루 디자인 탐색은 운영 화면이나 운영 브랜드를 바꾸지 않습니다.

독자용 최신 시안은 **알림 하나 → 뉴스 메일 한 통 → 그 안에서 모든 기사 이어 읽기**입니다. `/newsletter-prototypes/notifications.html`에는 기사별 알림 대신 전체 메일 알림이 하나만 표시되고, `mail.html?date=2026-09-16`을 열면 `letter.html`의 모든 기사가 한 문서에 이어집니다. 각 기사에는 제목·원본 비율 사진·핵심 요약·쉬운 설명·배경/중요성·원문이 있으며, 목차를 누르면 별도 기사 화면이 아니라 같은 메일 안의 해당 부분으로 이동합니다. 처음부터 끝까지 스크롤해서 읽어도 됩니다. 메일 맨 아래에는 처음으로 돌아가기 링크가 있습니다.

이전의 `read.html`/`story-<id>.html`은 개별 기사 디자인을 살펴본 로컬 참고 파일일 뿐 기본 알림의 목적지가 아닙니다. 세 열 비교도 디자인 검토용으로만 남습니다. 메일 시안은 발송 기능을 포함하지 않으며, 실제 OS 알림 표시·구독자·평일07:30 운영 설정을 바꾸지 않습니다. 실제 이메일 발송은 별도 연결 전입니다.

최신 디자인 보완은 중복된 세 줄 요약 패널과 긴 안내를 덜어내고, 하나의 간결한 목차 다음에 모든 기사를 보여줍니다. 기사 안에서는 분야·실제 읽기 순서 → 제목 → 핵심 한 줄 → 원본 비율 사진 → 쉬운 설명 → 차분한 배경 → 중요성·원문으로 위계를 정리했습니다. 파란 잉크의 머리글과 이 시안에서만 쓰는 블루·옐로 메일 아이콘으로 톤을 맞췄으며 운영 로고는 바꾸지 않았습니다. 기존 frontend-design·UI/UX Pro Max 가이드를 읽고 읽기 폭·줄 높이·제목 줄바꿈을 점검했습니다. 이후 설치된 Product Design 워크플로로 현재 로컬 화면을 새로 캡처·검토했고, 각 기사 끝에 같은 메일의 `목차로 돌아가기` 링크를 추가했습니다. 새 페이지나 추가 알림은 생기지 않습니다. 검토 기록과 한계는 `frontend/test-results/product-design-audit-20261104/notes.md`에 있습니다. 별도 유료 디자인 서비스나 뉴스 생성 API는 새로 연결하지 않았습니다.

## 품질 기준

변경 사항은 프런트 린트·빌드·브라우저 E2E와 백엔드 검증을 통과한 뒤 운영에 반영합니다. 콘텐츠를 추가하거나 고칠 때도 다음을 확인합니다.

- 첫 화면에서 오늘 무엇을 읽는지 바로 이해되는가
- 요약과 상세 내용이 중복되지 않고 자연스럽게 이어지는가
- 출처와 불확실성이 숨겨지지 않았는가
- 모바일·데스크톱에서 이미지와 본문이 안정적으로 보이는가
- 알림 등록과 해지 흐름이 한 번에 이해되는가

### 실행·검증·운영 구성

Next.js16/React19 정적 프런트(nginx) → 같은 출처 `/api` 프록시 → Kotlin/Spring Boot4/JPA → PostgreSQL 구조입니다. `DailyBriefingLetter.tsx`와 `NewsEditionIndex.tsx`는 일반 뉴스 화면, `ReceivedBriefing.tsx`는 알림으로 들어오는 읽기 화면, `frontend/lib/newsletter/`는 메일 시안 렌더링을 담당합니다. 이메일 전송 제공자/SMTP는 연결하지 않았으며 실제 OS 알림 모양은 기기에 따라 달라집니다.

Node22와 패키지에 지정된 pnpm, 백엔드는 JDK21·Maven을 사용합니다.

```bash
cd frontend
pnpm install --frozen-lockfile
pnpm lint
node --experimental-strip-types --test tests/daily-letter.test.mjs tests/newsletter-renderer.test.mjs tests/reader-article-renderer.test.mjs
pnpm build
pnpm dev
# 별도 터미널: cd backend && mvn --batch-mode verify
# 로컬 API 실행: cd backend && mvn spring-boot:run
```

데이터베이스 스키마는 `backend/src/main/resources/db/migration/`의 Flyway 마이그레이션을 사용합니다. 운영 PostgreSQL을 로컬 테스트 DB로 사용하지 마세요. API 건강 상태는 `/actuator/health`로 확인하며 실제 배포 프록시 설정은 `frontend/nginx.conf.template`을 따릅니다. 운영 관리용 API·키·등록 기기 정보는 공개 화면/로그/테스트 증거에 포함하지 않습니다.

| 환경변수 | 용도 | 필요 여부·설정 위치 |
| --- | --- | --- |
| `NEXT_PUBLIC_API_BASE_URL` | 별도 출처 API를 쓰는 경우의 공개 URL | 선택; 운영은 같은 출처 프록시 |
| `NEXT_PUBLIC_BASE_PATH`, `NEXT_PUBLIC_SITE_URL` | 정적 호스팅 경로·공개 사이트 주소 | 선택; Next 빌드 환경 |
| `BACKEND_URL` | nginx가 연결하는 내부 API 주소 | 운영 필수; Coders 서비스 참조 |
| `DATABASE_URL`, `DATABASE_USER`, `DATABASE_PASSWORD` | 관계형 DB 연결 | 운영 필수; Coders PostgreSQL 리소스 |
| `OPENAI_API_KEY` | 기존 뉴스 생성 인증 | 생성에 필요; OpenAI Platform 발급 후 서버 비밀 환경변수 |
| `NEWS_MINIMUM_IMPORTANCE_SCORE` | 발행 후보의 최소 중요도 | 선택; 운영 기본 65. 여러 곳에서 보도되어도 이 기준을 낮추지 않음 |
| `NEWS_MAX_AI_CANDIDATES` | 한 라운드의 요약 후보 예산 | 선택; 운영 기본 120. 발행 기사 수와 별개 |
| `NAVER_CLIENT_ID`, `NAVER_CLIENT_SECRET` | 기존 뉴스 검색 인증 | 해당 수집기 사용 시; 네이버 개발자센터 발급 |
| `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` | 기존 알림 서명 키 | 알림에 필요; 기존 서버 설정 보존·임의 재발급 금지 |
| `BRIEFING_ADMIN_TOKEN` | 운영 관리 인증 | 관리 기능에 필요; 서버 비밀 환경변수 |

정확한 전체 변수명·기본값·조건은 `backend/.env.example`, `backend/src/main/resources/application.yml`, `coders.yaml`이 기준입니다. 위 표에는 인증값이나 토큰을 기록하지 않습니다. 운영에 이미 있는 인증값은 UI 변경 때문에 새로 발급하거나 덮어쓰지 않습니다.

### 실제 요약 확인과 내 기기 알림

수동 운영 작업 `regenerate-only`는 오늘 에디션을 실제 API로 다시 요약하되 알림은 보내지 않습니다. `regenerate-all`은 전체 알림까지 보내는 별도 작업이므로 본인 확인용으로 실행하지 않습니다. 새 결과가 준비되기 전에는 기존 뉴스가 유지되며, 재생성이 빈 결과로 끝나도 기존 읽을 수 있는 뉴스는 지우지 않습니다. 실제 API 사용 비용이 발생하므로 실행 전 운영자 승인이 필요합니다.

알림이 등록된 기기의 설정 화면에서 `내 기기 알림 테스트`를 누르면 그 기기에만 실제 브리핑의 제목·대표 요약과 발행일 링크를 보냅니다. 당일 정기 발송 기록은 소모하지 않으며, 다른 사람의 기기를 오래된 등록 순서만으로 운영자 기기라고 추정하지 않습니다. 새 알림을 누르면 같은 날짜의 `/briefing/delivery/` 뉴스레터를 엽니다. 서버의 푸시 제공자 접수 성공과 휴대폰에서의 실제 수신은 구분하며, 최종 수신은 해당 기기에서 확인해야 합니다.

```bash
# 기존 GitHub Actions의 관리자 시크릿만 사용; 키를 로컬로 복사하지 않음
gh workflow run morning-briefing.yml -f operation=generation-status -f send_telegram_report=false
gh workflow run morning-briefing.yml -f operation=regenerate-only -f send_telegram_report=false
node --test scripts/morning-operations.test.mjs
```

### 뉴스 AI 모델 (기존 키 유지)

2026-11-04 승인 조합은 `OPENAI_CANDIDATE_MODEL=gpt-6.1-terra`, `OPENAI_EDITOR_MODEL=gpt-6.1-sol`입니다. 네이버·공식 RSS가 기사를 수집하고 Terra가 후보의 사실 기반 요약·쉬운 설명·중요도를 작성합니다. Sol은 적격 후보의 첫 순서만 정하며, 나머지 중요한 기사를 목록에서 지우거나 본문을 새로 쓰지 않습니다. 기존 `OPENAI_API_KEY`·발송·수집 주기·요약 호출 예산은 유지합니다.

15건 발행 상한·분야별 상한과 숫자를 채우기 위한 목표값을 제거했습니다. 전날 보도 중 중요도·추천·출처 교차 확인·중복 제거를 통과한 기사만 제공하므로, 발행량은 날짜마다 달라집니다. 보도 출처가 많아도 중요도나 근거가 부족하면 제외합니다. 스포츠·e스포츠는 조건을 통과하면 포함하고, 없어도 다른 뉴스의 발행은 막지 않습니다. 이미 발행한 과거 에디션의 건수는 자동으로 늘어나지 않습니다.

두 모델의 [Responses/Structured Outputs 지원](https://developers.openai.com/api/docs/guides/latest-model)과 각 모델의 추론 설정을 공식 문서에서 확인했습니다. 기존 `low` 요약/`medium` 편집, 출력 토큰5000/3000, `store:false`와 엄격한 JSON 출력 계약은 유지합니다. 공개 모델 지원 여부는 해당 운영 계정의 실제 접근 권한을 보장하지 않으며, 키를 로컬로 복사하거나 새로 발급하지 않습니다. 운영 적용은 새 배포의 `ready`와 동작 확인 후에만 완료로 판단합니다.

[Terra 가격](https://developers.openai.com/api/docs/models/gpt-6.1-terra)은 Standard100만 입력/출력 토큰당$1/$5, [Sol 가격](https://developers.openai.com/api/docs/models/gpt-6.1-sol)은$2/$10입니다(2026-11-04 확인, 실제 사용 시 최신 가격 참조). 현재 설정은 수집6회+최종화1회에 회당 최대120후보, 최대840회 요약이므로 호출당 입력2000/출력1500토큰 가정 시 요약비만 약$7.98/평일입니다. 이는 실제 사용량 견적·상한·보장 금액이 아니며 최종 편집/추론 토큰·재시도·긴 입력에 따라 달라집니다. 반복 호출 수나 비용 제한을 이번 모델 변경에서 임의로 바꾸지 않았습니다.
