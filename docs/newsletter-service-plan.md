# 아침결: 메일을 읽는 경험에서 서비스로

## 승인 후 실제 서비스 연결 (2026-11-04)

사용자가 선택 디자인의 운영 적용·GitHub 반영·배포를 명시적으로 승인했다. `/briefing/`은 이제 `DailyBriefingLetter`에서 실제 날짜별 API 데이터를 편지형으로 읽는다. 아래 프로토타입의 정적 보관 기사나 예시 데이터를 운영 실패 시 대체 뉴스로 사용하지 않는다.15개·적은 수·스포츠 없는 결과도 받은 그대로 모두 표시하며, 원본 비율 사진·쉬운 설명·배경·출처·목차 복귀·글자 크기·관심도/오류 신고를 보존한다. 기존 알림 구독과 평일07:30 스케줄·백엔드·생성 모델은 변경하지 않는다.

실제 전송 채널은 여전히 웹 알림이다. 이메일/SMTP 제공자를 새로 연결하거나 이메일 수신자를 수집한 것은 아니다. 아래의 ‘미배포·발송하지 않음’ 설명은 최초 시안 제작 당시의 범위이며, 이번 승인 후 운영 UI 배포와 구분한다. 실제 이메일 발송은 별도 승인·연결·수신함 검증이 필요하다.

## 이번에 제공하는 범위

운영 서비스를 바꾸지 않고, 비교할 메일 디자인 3개와 실제 HTML·텍스트 생성기를 추가한다. 발신 서비스 연결·사용자 이메일 수집·배포·발송은 하지 않는다.

현재 아침결은 웹 푸시와 웹 뉴스 리더를 제공한다. 기존 `EditorialStudio`의 Email 채널은 “발신 도메인·SMTP 연결 대기”이며 실제 이메일 발송 기능이 아니다. 기존 알림 등록은 이메일을 수집하지 않는다. 화면의 메일 모양과 실제 이메일 전송은 구분해야 한다.

## 독자 경험과 디자인 선택

현재 사용자 확정 방향은 **전체 알림 한 번 → 전체 뉴스 메일 한 통**이다. 기사별 알림/개별 기사 페이지를 여는 이전 해석은 잘못됐으므로 기본 흐름에서 제외했다. 메일 안에서 각 기사를 차례로 읽고, 목차로 같은 메일의 원하는 기사에 바로 내려간다. 한 편씩 읽는다는 뜻은 기사별 알림을 여러 번 보낸다는 뜻이 아니다. 아래 세 템플릿은 디자인 대안이며 세 통을 보낸다는 뜻도 아니다.

디자인 보완에서는 중복 요약 패널을 제거하고, 큰 머리글과 간결한 목차 → 각 기사의 제목·핵심 한 줄·사진·18px 쉬운 설명·차분한 배경·원문으로 위계를 정리했다. 뉴스 데이터는 보존했으며 순서 표시는 중요도 점수가 아니라 실제 읽기 위치다. 시안 전용 자체 메일 아이콘을 더했고 운영 자산은 바꾸지 않았다. 당시 단위22개·빌드/타입/린트, 최종 핵심 브라우저14개가 통과했다. 첫 전체 검사27/28에서 드러난 iPhone FontFaceSet 상태 전제는 실제 차단 요청/읽기 결과 검사로 고쳤다. 최종 결과를28/28로 보고하지 않는다. 이 단계의 증거는 `frontend/test-results/newsletter-editorial-polish/`에 있다.

이후 Product Design이 설치되어 해당 스킬의 화면 우선 검토를 실행했다. 새 앱 내 브라우저 캡처에서 긴 메일을 읽은 뒤 목차로 복귀하기 어려운 점을 확인하고, 각 기사 끝에44px 높이의 같은 문서 목차 링크를 추가했다. 이번 최종 단위23개·빌드/타입/린트가 통과했으며 앱 내 브라우저에서360/390/768/1440 CSS 폭과 실제 링크·키보드 복귀를 확인했다. 이번 단계에 Playwright CLI 검사를 새로 실행한 것은 아니며, 기존14개 결과와 구분한다. 새 검토 기록은 `frontend/test-results/product-design-audit-20261104/notes.md`다. 외부 사람의 독립 리뷰·실제 독자 조사·실제 수신함 검증을 받은 것은 아니다.

| 시안 | 독자가 받는 경험 | 구성 | 추천 용도 |
| --- | --- | --- | --- |
| 아침편지 | 모든 기사를 한 편씩 충분히 이해하며 읽는 뉴스 | 인사 → 전체 목차 → 기사별 요약·사진·쉬운 설명·배경·원문·목차 복귀 | 기본형 추천 |
| 모닝브리프 | 바쁠 때 중요한 것부터 골라 읽기 | 짧은 결론 → 작은 사진과 기사별 원문 | 빠른 탐색 선호 독자 |
| 데일리픽 | 사진을 보고 맥락으로 이어지는 뉴스 | 대표 사진과 설명 → 다른 분야의 포토 인덱스 | 비주얼 선호 독자 |

색만 바꾼 시안이 아니다. 같은 2026-09-16 보관 기사 6개를 사용하되 읽기 순서와 사진 비중이 다르다. 원문을 이번 작업에서 독립적으로 다시 검증한 것은 아니며, 미리보기에는 보관 날짜를 명시한다.

선택 전에는 실제 수신자에게 A/B 발송하지 않는다. 다음 검토에서는 1) 첫 핵심을 찾는가, 2) 사진 없이도 이해되는가, 3) 원문으로 이동하는가, 4) 글자 크기가 편한가를 소수 자발적 참여자에게 확인한다. 성과 수치를 미리 만들어내지 않는다.

## 구현한 재사용 기반

- `frontend/lib/newsletter/render-newsletter.mjs`: 저장된 브리핑 JSON을 HTML + plain text + subject + preheader로 바꾸는 순수 렌더러. 네트워크·키·수신자 DB·발송 로직이 없다.
- 세 가지 본문 구성을 분리하고 안전한 URL·HTML 이스케이프·출처·푸터만 공유한다.
- 기본값은 미리보기. 실제 발송용 렌더링에는 발신자 정보와 HTTPS 수신 거부 URL을 요구한다. 이는 발송 도메인 인증이나 법적 검토를 완료했다는 의미가 아니다.
- 표 기반 배치, 인라인 핵심 스타일, 기본 한국어 글꼴, 원본 사진 비율, 이미지가 없어도 남는 본문, 15개 상한과 90 KiB HTML 상한을 적용한다.
- 기본 메일에는 JS·폼·SVG·원격 웹폰트·추적 픽셀·자동 재생이 없다. 사용권을 확인한 폰트를 명시적으로 설정할 때만 `@font-face`를 추가할 수 있으며, 웹폰트를 지원하지 않는 메일앱은 시스템 서체로 읽힌다.
- `frontend/public/newsletter-prototypes/index.html`: 시안 선택, 휴대폰/컴퓨터 너비, 새 창 열기, HTML 다운로드, 텍스트 버전 확인. 정적 로컬 비교 화면이다.
- `frontend/public/newsletter-prototypes/compare.html`: 실제 세 HTML 메일 전체를 나란히 비교하고 모바일에서는 세로로 이어 읽는다. 상단·설명·제목·분류·조작을 `theme.css`와 같은 SUIT 서체로 맞춘다. `preview-frames.js`가 두 미리보기 화면의 본문 높이를 이미지·폰트·너비 변경 후 재측정한다.
- `frontend/public/newsletter-prototypes/notifications.html`: 전체 메일 알림을 정확히 하나만 보여준다. 기사별 알림은 생성하지 않는다.
- `frontend/public/newsletter-prototypes/mail.html`: 알림에서 열리는 전체 뉴스 메일. 날짜·제목·발신 브랜드와 모든 기사 본문을 이어 보여준다. 목차는 같은 메일의 각 기사로 이동한다. 메타정보 실패 시 읽을 수 있는 본문을 숨기지 않고, 본문 실패 시 재시도와 직접 열기를 제공한다.
- `frontend/public/newsletter-prototypes/read.html`: 이전 개별 기사 디자인 참고 파일이며 현재 기본 흐름이나 알림 목적지가 아니다. 실제 API/발송은 연결하지 않았다.
- `frontend/scripts/export-newsletter-prototypes.mjs`: 기존 보관 fixture로 비교 파일을 내보낸다. 메일을 보내지 않는다.

현재 기본 진입은 `notifications.html`의 알림 하나이며, `mail.html?date=2026-09-16`에서 전체 `letter.html`을 한 번에 읽는다. 기사마다 다시 열거나 이전/다음으로 넘길 필요가 없다. 전체 목차와 `#news-1` 등의 연결은 같은 HTML 메일 안에서만 이동한다. 기존 날짜와6개 보관 기사를 사용하며 새로운 기사나 발신 이메일 주소를 임의로 만들지 않았다. 운영 알림/이메일 발송이나 주기는 변경하지 않았다.

이 수정의 최종 검사는 단위21개, Chromium6개+iPhone WebKit6개=12개, 빌드·TypeScript·ESLint를 통과했다. 알림1개/전체메일1개/기사6개, 같은 메일 내 이동, 오류 재시도와 메타정보 실패 시 본문 유지,4개 화면폭·사진/폰트 차단·글자2배를 검증했다. 실제 기본 메일 HTML은40,620bytes이며 잘라내지 않았다. 새 증거는 `frontend/test-results/newsletter-digest-mail/`에 있다. 아래 개별 기사 시안의 이전 검증 기록은 역사적 참고이며 현재 알림 흐름이 아니다.

이 변경의 검증은 렌더러16개, Chromium6개 + iPhone WebKit6개 시나리오, 빌드·TypeScript·정적 출력·ESLint를 통과했다.6개 기사 이동과 이력·포커스,360/390/768/1440폭, 정적 파일 오류 재시도, 사진/폰트 미지원, 글자2배를 확인했다. 첫 검사에서 발견한 뒤로 가기 오류를 수정한 뒤 관련12개 시나리오를 재실행했다. 이 검증은 실제 메일 발송이나 운영 사이트 적용이 아니다.

알림→기사 후속 시안의 최종 검사는 단위20개와 Chromium8개+iPhone WebKit8개=16개, 빌드·TypeScript·ESLint를 통과했다. 모바일 터치/PC키보드,6개 정확한 기사 연결·직접 주소 새로고침·복사/권한거절·오류 재시도와 위4개 화면폭을 확인했다. 캡처에서 발견한 아이폰 소수점·금액 줄바꿈을 수정하고 전체16개를 다시 검사했다. 결과는 `frontend/test-results/newsletter-notification-flow/`에 있으며 실제OS알림 전달이나 이메일 발송 검증이 아니다.

```powershell
cd frontend
node scripts/export-newsletter-prototypes.mjs
node --test tests/newsletter-renderer.test.mjs
npm.cmd run build
```

로컬 정적 서버를 실행한 뒤 `/newsletter-prototypes/`를 연다. `127.0.0.1` 주소는 해당 PC에서만 열리므로 휴대폰으로 확인할 때는 제공한 스크린샷을 사용한다. 외부 미리보기 링크는 별도 공개 허가 후에만 만든다.

### 잘림·간격과 폰트 보완

- 제목·본문은 줄임표나 고정 높이로 자르지 않는다. 사진을 제목 아래에 두고 원본 가로세로 비율로 표시한다.
- 본문17px / 줄 높이1.65, 제목22–25px / 1.4, 모바일 안쪽 여백20px을 기준으로 사용한다. 기사 사이 여백과 사진·설명 사이 간격을 일관되게 둔다. [실제 서비스 비교 근거](newsletter-reference-audit.md)를 관찰하고 값의 선택 이유를 기록했다.
- 갤러리는 본문·이미지·서체·너비가 바뀔 때 iframe 높이를 다시 측정한다. 메일 끝까지 한 페이지에서 스크롤하며, 브라우저가 로컬 파일 접근을 막을 때는 새 창 링크와 기본 스크롤을 유지한다.
- 최신 사용자 정정에 따라 토스 폰트 파일을 기다리지 않고, 뉴닉에서도 선언을 확인한 공개 SUIT 계열을 공식 배포처에서 가져왔다. 토스 전용 폰트와 다르며 사용자에게 파일 제공을 요구하지 않는다. 아이폰 캡처 검토 후 가변 파일 대신 굵기가 안정적인 Regular·SemiBold·Bold 세 파일을 선택했다.
- `public/newsletter-prototypes/fonts/`에 수정하지 않은 SUIT 파일과 원본 OFL을 포함했다. `font-config.json`에 배포처·고정 커밋·해시·사용권·폰트 경로를 기록하고 메일과 갤러리의 실제 서체 이름을 일치시켰다. 미리보기 상대 경로는 `./fonts/<filename>`만 허용하고 실제 메일용 설정은 허가된 HTTPS 주소를 요구한다. 브라우저에서 파일 로딩과 한국어 글리프 렌더링을 확인한다.
- 실제 Gmail·Apple Mail·Outlook 수신함 검증과 아침결 독자 대상 선호·이해도 조사는 미완료다. 전체 길이 스크린샷은 브라우저 시안 검증용이며 수신함 호환성을 보장하지 않는다.
- 사용자가 비교 이미지의 상단을 표시하며 메일 바깥 글꼴과 전체 디자인도 같은 수준으로 요청했다. 예전 합성 이미지의 상단 시스템 서체 문제를 없애기 위해 실제 비교 HTML에서 캡처한다. 토스피드의 읽기 위계를 참고하되 전용 폰트·로고·화면은 복제하지 않는다. 전체 프로토타입에 중립 잉크와 절제된 블루를 적용하며, 운영 UI는 변경하지 않는다.

## 서비스 연결의 다음 단계와 완료 조건

1. **디자인 결정**: 기본 시안 1개 선택. 짧은 설명/배경 설명 비중과 메일에 포함할 기사 수를 확정한다. 데이터 구조는 기존 브리핑을 재사용한다.
2. **메일 채널 승인과 연결**: 사용자가 발신 도메인과 발송 제공자를 선택한다. 비용·서비스 가입·도메인 변경은 별도 승인 대상이다. 운영 키는 서버 환경변수에만 둔다. SPF/DKIM/DMARC, 발신자 연락처, 메일앱 호환성 검증을 연결 전 체크리스트로 둔다.
3. **수신 동의와 해지**: 이메일 수집 목적과 보관·삭제 정책을 먼저 알리고 명시적 신청/확인 흐름을 만든다. 기존 웹 푸시 구독자를 임의로 이메일 구독자로 전환하지 않는다. 해지·반송·스팸 신고는 즉시 재발송 대상에서 제외하고 UI에서도 같은 상태를 보여준다.
4. **발송의 정확성**: 평일 07:30 Asia/Seoul 기준을 기존 서비스와 맞춘다. 브리핑 날짜 + 구독자 + 채널의 중복 방지 키, 아웃박스/큐, 제한된 재시도, 제공자 응답/실패 기록을 둔다. “제공자 접수”와 “기기 표시/수신함 도착/읽음”은 다른 상태다.
5. **내용과 화면의 일치**: 발송한 메일은 그날의 본문 스냅샷으로 보존한다. 웹 리더는 날짜와 최신 확인 시점을 보여주고, 앱 복귀·연결 회복 시 재확인한다. 기사 없는 안내를 뉴스 완성본처럼 표현하지 않는다. 스포츠·e스포츠가 없다는 이유로 다른 중요 뉴스를 누락시키지 않는다.
6. **안정성과 비용**: 기사 요약은 수신자별로 반복 생성하지 않고 저장된 브리핑을 공유한다. 메일 실패와 기사 생성 실패를 별도 관측한다. 운영자에게 실제 조치가 필요한 실패만 알리고, 사용량·발송량·대기열·반송률을 확인 가능하게 한다. 추가 지출 한도는 사용자가 결정한다.
7. **검증 후 소규모 시작**: 실제 Gmail·Apple Mail·Outlook의 수신함에서 이미지 차단·다크 모드·긴 제목·수신 거부·중복·재시도까지 확인한다. 브라우저 스크린샷이나 빌드 성공만으로 실제 수신함 검증을 대신하지 않는다. 담당자 본인 테스트도 승인을 받고 발송한다.

## 수익화 이전에 지킬 핵심

첫 상품은 화려한 설정 화면이 아니라 “정시에 도착하고, 믿을 수 있고, 쉽게 읽히는 한 통”이다. 무료 핵심 뉴스 품질을 유지한 뒤, 구독자가 실제로 원하는 관심 분야 우선순위·읽기 깊이·저장/검색 같은 기능부터 검증한다. 유료 전환율·구독자 수·수익을 가정해 화면에 표시하지 않는다.
