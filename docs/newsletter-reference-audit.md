# 아침결: 독자에게 익숙한 읽기 경험 조사

## 범위와 근거의 한계

2026-11-04에 네이버 뉴스·뉴닉·어피티·토스피드의 공개 홈/목록과 실제 기사 상세를 Chromium에서 직접 열었다. 1440×1000 및 390×844에서 화면을 보고 computed CSS를 수집했다. 기록과 스크린샷은 `frontend/test-results/newsletter-user-research/`에 있다. 이 목록은 트래픽 순위 조사나 아침결 사용자의 방문 기록으로 선정한 것이 아니다. 한국어 뉴스·뉴스레터·설명형 콘텐츠라는 사용 목적에 가까운 비교 사례다.

CSS의 font-family 선언은 실제 모든 글리프의 사용 서체를 보장하지 않는다. 따라서 외부 서비스의 서체를 단정할 때는 선언값이라는 한계를 남기고, 아침결 구현에서는 폰트 파일 로딩과 한국어 실제 렌더링도 별도로 확인한다. 화면 관찰로 읽기 성과나 다수 사용자의 선호가 입증된 것은 아니다.

## 이번 구현 판단

사용자는 '내 기준의 예쁨'이 아니라 독자가 익숙하게 읽는 서비스를 분석해 적용하라고 정정했다. 이전의 '토스 파일 첨부 대기'를 이번 작업의 차단 조건으로 삼지 않는다.

- **SUIT**를 공식 배포처에서 고정 버전으로 가져온다. 뉴닉과 같은 설명형 읽기 사례에서 확인한 공개 UI 본문용 서체 계열이며 토스 폰트로 부르지 않는다. [공식 소개·배포](https://github.com/sun-typeface/SUIT), [OFL-1.1](https://github.com/sun-typeface/SUIT/blob/main/LICENSE). 처음에는 Variable을 검증했으나, 아이폰 WebKit 캡처에서400/700의 시각적 굵기 차이가 약해 보여 Regular·SemiBold·Bold를 따로 지정한다. 가변 파일은 조사 폴더에 보존하고 미리보기 배포 자산에는 포함하지 않는다. 이 선택은 육안 검증을 통해 보완한 구현 판단이다.
- 메일 본문은17px/1.65, 기본 굵기400, 제목은22–25px/1.4·700. 여러 서비스에서 관찰한 범위 안에서 모바일 메일과15개 기사까지의 스크롤 길이를 고려한 구현 판단이며, 통계적으로 '최적'임을 주장하지 않는다.
- 본문은 `#191f28`, 설명은 `#4e5968`의 중립적인 잉크색으로 바꾸고 기존 초록·파랑은 브랜드와 링크에만 쓴다. 흰 본문 배경은 유지한다.
- 모바일 내부 여백20px, 데스크톱36px, 메일 최대640px을 사용한다. 작은 사진 옆 설명이 너무 좁아지지 않게 모바일 썸네일 폭을64px+16px 간격으로 줄인다. 제목은 전체 폭을 유지한다. 사진 자체는 원본 비율을 지킨다.
- 모바일의 인사·히어로는 짧게, 요약→제목→설명→원문이라는 기존 세 시안의 서로 다른 읽기 흐름은 유지한다. 카드를 더 장식하거나 불필요한 홈 화면을 추가하지 않는다.
- 웹폰트 미지원·차단 시 Apple SD Gothic Neo/Malgun Gothic 등 기기 서체로 읽히도록 같은 간격과 넘침 검증을 수행한다. 실제 메일앱에 SUIT가 반드시 표시된다고 약속하지 않는다.

## 사용자 중심 확인의 다음 단계

이번 변경은 비교 사례를 반영한 시안이다. 실제 독자가 첫 핵심을 찾는지, 요약 후 내용을 자기 말로 설명하는지, 원문을 찾는지, 기기별 글씨와 길이가 편한지를 자발적 사용자에게 확인해야 한다. 인기 서비스의 선택을 그대로 따랐다는 이유만으로 사용자 검증 완료로 간주하지 않는다. 새 추적기·분석 키·구독·유료 서비스는 추가하지 않는다.

## 이번 로컬 검증 결과

- Next.js 빌드·TypeScript·정적 출력, 변경 파일 ESLint, 렌더러 테스트12개 통과.
- 최종 Regular·SemiBold·Bold 구성으로 Chromium7개 + iPhone WebKit7개, 총14개 시나리오 통과.
- 세 굵기 파일이 실제 로드되는지, 한국어 제목이 SUIT 커스텀 폰트로 렌더링되는지, 굵은 글자의 획 면적이 본문보다 분명히 큰지 검사했다. 성공한 CSS 선언만으로 판단하지 않았다.
- 360×800·390×844·768×1024·1440×900에서 가로 넘침·사진 비율·전체 iframe 높이, 원문·다운로드·키보드 조작을 확인했다. 긴 한국어 제목, 2배 글자 확대, 이미지 차단·스타일 미지원·폰트 차단 시에도 본문과 마지막 푸터가 남는다.
- 세 전체 모바일 화면을 비교하고 각 전체 PC 화면을 직접 보았다. 캡처는 `frontend/test-results/newsletter-reader-first/`에 있으며 비교 이미지는 고정 높이로 자르지 않았다.
- 초기 실행에서는 이전 로컬 검증 서버가 종료되어 연결 거부가 발생했고, 다시 실행한 뒤 전부 재검증했다. 초기 가변 서체는 검사 통과 후 육안 비교에서 굵기 문제를 발견해 정적 서체로 바꿨다. 최종 결과는 `newsletter-reader-first-static-font-run` 실행 기준이다.
- 운영 뉴스·사용자·알림·API·PWA 코드는 이번 작업에서 바꾸지 않았고, 배포·메일/푸시 발송·커밋·푸시도 하지 않았다.

브라우저 검증은 실제 수신함 검증과 다르다. 실제 Gmail·Apple Mail·Outlook 발송과 아침결 독자의 선호·이해도 확인은 여전히 다음 단계다.

## 후속 요청: 메일 바깥 타이포그래피와 전체 톤

사용자는 전달한 비교 이미지의 상단 제목·설명·분류를 동그라미로 표시했다. 해당 이미지의 합성용 HTML은 메일과 달리 시스템 서체를 사용하고 있었다. `compare.html`에서 직접 메일 HTML을 렌더링하도록 바꾸어 상단까지 동일한 SUIT를 로드하고, 원본 UI와 결과 이미지가 따로 달라지지 않게 한다.

[토스피드](https://toss.im/tossfeed)와 [공개 기사 상세](https://toss.im/tossfeed/article/findyoursafezone-3a)의 읽기 위계·여백을 다시 참고했다. 이를 근거로 페이지 제목44/32px, 안내17–18px, 분류13–14px, 메타12px의 역할을 명시하고, 흰 바탕·중립 본문·블루 강조로 시안 전체를 통일한다. 이는 아침결만의 편집과 정보 구조를 유지한 참조이며 토스의 폰트·브랜드·자산을 복제한 것이 아니다. 기사 문구나 새 뉴스 데이터는 가져오지 않는다.

`theme.css`는 갤러리·전체 비교의 공통 서체와 토큰을 담당한다. 세 메일은 같은 색상 언어를 쓰되 편지형·빠른 요약형·포토형의 서로 다른 읽기 흐름을 유지한다. 운영 앱·백엔드·알림·독자 설정은 이 디자인 탐색의 대상이 아니다.

## 최신 메일 디자인 보완의 근거와 도구 범위

- 사용자 확정 흐름인 알림1개→전체메일1통을 유지한다. 기존의 세 줄 요약과 전체 목차가 연달아 나와 첫 기사까지의 스크롤이 길어지는 점을 코드·캡처에서 확인해 중복 요약 패널을 제거했다. 각 기사의 실제 핵심 요약은 그대로 보존한다.
- [SEED Typography](https://seed-design.io/foundations/typography)의 역할별 타입·계층 구분과 [Spacing](https://seed-design.io/foundations/spacing)의 일관된 간격/가장자리 여백을 참조했다. SEED 컴포넌트를 설치하거나 스택을 옮긴 것은 아니다. 아침결 본문에는 기존 SUIT를 유지하고 설명18px/1.75, 배경16px/1.75, 모바일20px 여백을 선택했다. 이는 특정 서비스 수치를 복제하거나 선호를 입증했다는 뜻이 아니다.
- [토스피드](https://toss.im/tossfeed)의 콘텐츠 중심 구조를 다시 참고하되 기사·폰트·로고·화면을 복제하지 않았다. 실제 뉴스 사진은 기존 출처 원본만 사용하며 생성 이미지를 뉴스 사진처럼 넣지 않았다.
- 기존 `../work/newsletter-reference-skills/`의 frontend-design·UI/UX Pro Max SKILL.md를 모두 읽었다. 후자의 로컬 검색 `reading line length`와 `orphan heading balance`는 읽기 폭,1.5–1.75 본문 줄 높이, 점진적 제목 균형 줄바꿈과 자연 폴백/의미 있는 제목 순서를 반환했다. 한국어 메일에 맞게 선택했으며 새로운 랜딩/일반 SaaS 템플릿은 사용하지 않았다.
- [Taste Skill](https://www.tasteskill.dev/)의 공개 개요는 확인했지만 redesign 지침의 시도한 raw 경로2개는404였다. 해당 지침을 읽거나 실행했다고 보고하지 않으며, 접근 가능한 기존 디자인 가이드를 사용했다.
- 당시 디자인 플러그인 검색에서 Figma·Canva·MagicPath·Product Design·Webflow는 설치되지 않은 상태였고 Product Design1개를 제안했다. 이후 앱이 Product Design 설치를 확인해 해당 스킬의 검토 워크플로를 실행했다. 현재 화면의 새 캡처로 알림→전체 메일→기사/목차 이동을 검토하고 각 기사 끝의 같은 문서 목차 복귀를 보완했다. 계정·전역 권한 변경·유료 서비스 가입·외부 소스 업로드는 하지 않았다. 새 증거와 한계는 `frontend/test-results/product-design-audit-20261104/notes.md`에 있으며 외부 사람의 독립 리뷰를 뜻하지 않는다.

후속 검증은 렌더러13개, Chromium9개 + iPhone WebKit9개, 빌드·TypeScript·정적 출력·변경 파일 ESLint 모두 통과했다. 상단 제목·설명·분류명의 실제 SUIT 글리프, 전체3개 메일의 본문/푸터 높이,360/390/768/1440폭과 폰트 미지원·확대·키보드·다운로드·갤러리↔비교 이동을 확인했다. 캡처는 `frontend/test-results/newsletter-editorial-ui/`에 있으며 데스크톱 전체·모바일 상단·모바일 메일을 직접 검토했다. 이 확인은 실제 메일 발송이나 대표 독자 선호 검증이 아니다.
